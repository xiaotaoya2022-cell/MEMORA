# Windows 的内存为什么"不回落"

这份文档解释 MEMORA 想解决的现象，以及它能证明什么、不能证明什么。

## 一、物理内存是页链，不是账户

Windows 不按"谁申请了多少"来记账。物理页在内核里分成几条链：

| 状态 | 含义 | 任务管理器算作 |
|---|---|---|
| Active / 工作集 | 进程当前映射着的页 | 已用 |
| Modified | 已修改、还没写回磁盘的脏页 | 已用 |
| Standby | 干净的文件缓存，随时可回收 | **可用** |
| Free | 空闲页 | 可用 |
| Zeroed | 已清零、可直接分配的页 | 可用 |

关键点：**Standby 算可用**。所以"关掉软件后内存没降"如果指的是任务管理器的
"已用"，那它和文件缓存无关——缓存本来就不计入已用。

## 二、常见的内存虚高来源

1. **进程仍然活着**。托盘图标消失不等于进程退出；很多软件退到后台继续驻留。
   任务管理器"详细信息"里按提交排序能看出来。
2. **共享页的延迟回收**。DLL、映射文件被多个进程引用时，最后一个引用释放前
   页不会消失。进程死了，句柄没关，页就还在。
3. **内核池泄漏**。分页池与非分页池由驱动分配，不属于任何进程。网卡/无线网卡、
   显卡、杀毒、虚拟化驱动的泄漏都发生在这里，典型特征是"非分页池"持续走高，
   对应 `Pool Tag` 分配次数远大于释放次数（甚至 0 释放）。
4. **会话空间与桌面堆**。每个登录会话有独立的窗口站与桌面堆；远程桌面、多用户
   切换、频繁创建窗口的程序会让它增长。
5. **内核 section 与驱动锁定页**。显卡驱动、AWE 分配、大页保留都可能持有物理页，
   它们不出现在进程工作集里。
6. **内存压缩**。Windows 10 以后，不常用的页会被压缩进 `Memory Compression`
   进程。它看起来只是一个进程，实际承载了本应写进页面文件的页。
7. **内核对象引用泄漏（僵尸 `EPROCESS`）**。进程早已退出、用户句柄早已关闭，但某个
   挂接了 `PsSetCreateProcessNotifyRoutine` 等回调的内核驱动（常见于终端安全软件、
   系统管家类过滤驱动或部分虚拟化驱动）持有 `ObReferenceObject` 引用未归还，
   导致 `EPROCESS`（`Proc` 池）、内存管理结构（`MiP2`）与令牌（`Toke`）长期滞留数以
   十万计、合计逾 GB；这类残骸必须更新或停用问题驱动后重启才能归零。
8. **Hyper-V / WSL2 虚拟化锁页（`Vid.sys`）与 NUMA 局部挤兑**。WSL2、Docker Desktop
   或虚拟机通过 `Vid` 分区直接锁走物理页（计入物理"已使用"，不计入普通进程工作集）；
   在多 NUMA 节点机器上还可能将其中某个节点压到仅剩几十 MB，引起局部卡顿而全局空闲看似充足。

## 三、为什么管家类软件看不见

绝大多数"内存优化"工具只枚举进程并累加工作集。这条路径天生漏掉第 3、4、5 类，
而且工作集本身还会因为共享页而重复计算。于是出现两个方向的错误：

- 把重复计算的工作集当成真实占用 → 高估进程，误杀无辜；
- 完全看不到内核池与会话空间 → 低估系统，得出"没有东西占内存"。

## 四、怎么自己验证

- **RAMMap**（Sysinternals）：看 Use Count、Standby、Modified、Paged/Nonpaged Pool。
  这是最接近真相的一张表。
- **poolmon**：按 pool tag 看内核池增长，能定位到具体驱动。
- **任务管理器 → 详细信息 → 提交大小**：按提交排序，比工作集更能说明"谁在占"。
- **性能监视器**：`Memory\Pool Nonpaged Bytes`、`Memory\Committed Bytes`、
  `Process(_Total)\Working Set`。

## 五、MEMORA 的判据

```
未归因提交 = 提交总量 − Σ进程私有提交 − 分页池 − 非分页池
```

- 用**私有提交**而不是工作集，避免共享页重复计算。
- 用**提交量**而不是物理占用，因为提交是精确记账，物理页状态会随缓存波动。
- 未归因部分为正是正常的；主路径已完整读取全部活跃进程私有提交，剩余差额主要来自共享 section、会话空间与驱动/虚机提交。
- 僵尸进程对象与驱动池异常：通过比对 `Process` 内核对象数、打开句柄数与 `Proc` 池分配/释放差，以及高占用 `Pool Tag` 对应的已加载 `.sys` 驱动，区分"正常后台缓存"与"内核不可释放泄漏"。
- 虚拟化与节点均衡：`status` / `doctor` 同时监测 Hyper-V/WSL2 `Vid` 锁页与各 NUMA 节点剩余内存，避免误把虚机锁页当成常规进程膨胀。
- 判断看**斜率**：单位时间内的持续增长，才叫异常；单点高低不算。

## 六、MEMORA 不做的事

- 不会因为"未归因提交很大"就去清缓存。那部分清不掉，清缓存只会让系统变慢。
- 不会为了让你看到数字下降而回收工作集。动作必须有原因，原因必须能验证。
- 不会在用户态强杀核心进程、篡改内核对象引用计数或强行卸载驱动。MEMORA 现已能在免提权、
  不启用 ETW 会话的条件下原生读取 `Pool Tag`、内核对象计数、`Vid`/NUMA 与驱动 `.sys` 映射，
  为你指明真实元凶；但它严守安全边界，只对用户态安全进程做克制的工作集与待机页管理，
  把驱动升级、排查与配置决策留给透明的归因报告。

## 七、读你自己的机器

`memora status` 的输出里，先看三行：

1. **物理内存**：真实使用率。若工作集合计远小于"使用"，说明大头不在用户态进程。
2. **内核池**：非分页池长期超过 1 GB，基本可以怀疑驱动。
3. **未归因提交**：结合无权限进程数量看。差值大且持续增长，才是"看不见的增长"。

`memora doctor --minutes 30` 会把这三条算成斜率，给出归因结论。它不会替你下
"一定是某个驱动"的断言，因为那需要更底层的证据。
